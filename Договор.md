Заказчик обязуется рассматривать результаты, давать по ним обратную связь и принимать их в порядке настоящего Договора.

Эти работы могут быть добавлены только отдельным изменением по разделу 7. Реализация спроектированного приложения планируется в следующем семестре курса.

## Приложение № 1. Техническое задание и состав результата

### 1. Цель проекта.

Подготовить согласованный комплект проектных документов приложения «ПослеЛекции», достаточный для его реализации в следующем семестре. Приложение делает опрос после лекции коротким и полезным: студент проверяет себя и отмечается на лекции, преподаватель получает аналитику понимания материала, обратную связь о лекции и учёт посещаемости без ручного сбора. Ключевой принцип: опрос не влияет на оценки студентов.

### 2. Платформы

- **Мобильное приложение** — для студента, Android / iOS (кросс-платформенная разработка).
- **Веб-версия** — для преподавателя, браузер с адаптивной вёрсткой.
- **Бэкенд** — серверная часть с REST API и ИИ-модулем на основе внешнего LLM API.

### 3. Функциональные контуры

- **Доступ и роли:** регистрация и вход по email и паролю с выбором роли (студент / преподаватель), восстановление пароля, разграничение доступа по ролям.
- **Лекции и опросы (преподаватель):** создание лекции и прикрепление текстовых материалов; настройка количества и типов вопросов, инструкции для ИИ и дедлайна; генерация кода доступа; ручное открытие и закрытие опроса.
- **Прохождение опроса (студент):** вход по коду, чат с ИИ-ботом, ответы в формате теста и короткого текста, мгновенная обратная связь, обязательный отзыв о лекции, итоговая справка, история опросов и диалогов.
- **Аналитика (преподаватель):** число прошедших опрос в реальном времени, посещаемость и средний уровень понимания, два ИИ-саммари (по ответам и по отзывам), просмотр диалогов, комментарий преподавателя с push-уведомлением студенту.
- **ИИ-модуль:** генерация уникальных наборов вопросов по материалам лекции, проверка коротких ответов по смыслу, обратная связь студенту и саммари для преподавателя — на уровне требований, сценариев и схем данных, без подключения реального API.

### 4. Нефункциональные требования

В документации должны быть отражены: время ответа API не более 2 секунд при 50 одновременных пользователях; поддержка Android 10+ и iOS 14+; работа веб-версии в актуальных Chrome, Firefox и Safari; хранение паролей в виде хеша и передача данных по HTTPS; интерфейс на русском языке; корректная работа приложения при переключении между Wi-Fi и мобильным интернетом.

| № | Результат | Минимальные критерии |
|---|---|---|
| 1 | Требования | Цель, роли, сценарии студента и преподавателя, функциональные и нефункциональные требования с идентификаторами, критерии приёмки, границы проекта. |
